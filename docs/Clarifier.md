# Clarifier 需求澄清 Agent

你现在的问题其实发生在执行之前：

```text
用户需求
   ↓
需求澄清 Agent
   ↓
完整/可执行的 Specification
   ↓
Executor Agent
   ↓
Tool
   ↓
Result
   ↓
Judge
   ↓
PASS / FAIL
```

### 这个 Agent 的职责

它不是让模型“自己把需求做完”，而是：

> **发现需求中的歧义、缺失约束、边界条件，并主动向用户提问，把自然语言需求转换成明确的可执行规格。**

比如用户说：

> “给用户增加一个删除订单的接口。”

Clarifier 不应该直接让 Executor 开干，而是发现：

* 删除是物理删除还是软删除？
* 已支付订单能不能删除？
* 已发货订单呢？
* 谁可以删除？
* 删除后关联订单明细怎么办？
* 是否需要记录操作日志？
* 是否需要幂等？
* API 返回什么？
* 删除失败怎么办？

于是它产生：

```text
Clarifier
  ↓
我需要确认几个问题：

1. 已支付订单允许删除吗？
2. 删除采用软删除还是物理删除？
3. 删除后订单明细如何处理？
4. 是否需要记录操作日志？
```

用户回答之后：

```text
原始需求
+
用户补充
↓
Specification
↓
Executor
```

---

### 我更建议你把它设计成三个 Agent

实际上 Orca 这个架构已经可以往一个很漂亮的方向发展：

```text
                 ┌──────────────────┐
                 │  Requirement     │
                 │  Clarifier       │
                 └────────┬─────────┘
                          │
                    Specification
                          │
                          ▼
                 ┌──────────────────┐
                 │    Executor      │
                 │                  │
                 │   LLM + Tools    │
                 └────────┬─────────┘
                          │
                     Candidate
                          │
                          ▼
                 ┌──────────────────┐
                 │      Judge       │
                 │                  │
                 │ 是否真的完成？    │
                 └────────┬─────────┘
                          │
                   ┌──────┴──────┐
                   │             │
                 PASS           FAIL
                   │             │
                   ▼             ▼
                  Done        Executor
```

三个角色其实非常清晰：

| Agent         | 解决的问题             |
| ------------- | ----------------- |
| **Clarifier** | “你到底想让我做什么？”      |
| **Executor**  | “我怎么把它做出来？”       |
| **Judge**     | “你做出来的东西真的符合要求吗？” |

我甚至建议你不要把第一个叫 `Planner`。

因为 **Planner 是怎么做，Clarifier 是做什么**。

这是两个完全不同的问题。

---

### 而且 Clarifier 最好不是“一定要提问”

这是设计上很重要的一点。

它应该有三个状态：

```json
{
  "status": "ready"
}
```

表示：

> 需求已经足够明确，可以执行。

或者：

```json
{
  "status": "question",
  "questions": [
    {
      "id": "delete_policy",
      "question": "已支付订单是否允许删除？"
    }
  ]
}
```

表示：

> 缺信息，需要用户回答。

甚至：

```json
{
  "status": "assumption",
  "assumptions": [
    "未明确说明，默认采用软删除",
    "未明确说明，默认只有管理员可以删除"
  ]
}
```

这个特别有价值。

因为**不是所有歧义都值得问用户**。

否则一个简单需求：

> “给 User 增加一个 email 字段。”

Clarifier 如果开始问：

> “email 是否允许为空？”
>
> “是否需要唯一？”
>
> “是否需要索引？”
>
> “是否需要验证 RFC 规范？”
>
> “是否需要脱敏？”

用户会疯掉。

所以可以让它遵循：

```text
歧义
 ↓
是否影响实现结果？
 ↓
 ├── 否 → 合理假设
 │
 └── 是
      ↓
   是否能从项目现有约定推断？
      ↓
      ├── 能 → 使用项目约定
      │
      └── 不能 → 向用户提问
```

---

### 这样你的 Orca 就从“Coding Agent”变成了一个完整闭环

我觉得这比单纯加 Judge 更有意思：

```text
                  ┌──────────────┐
                  │    User      │
                  └──────┬───────┘
                         │
                         ▼
              ┌────────────────────┐
              │ Requirement        │
              │ Clarifier          │
              └─────────┬──────────┘
                        │
                 Specification
                        │
                        ▼
              ┌────────────────────┐
              │ Executor           │◄────┐
              │                    │     │
              │ LLM + Tools        │     │
              └─────────┬──────────┘     │
                        │                │
                    Candidate            │
                        │                │
                        ▼                │
              ┌────────────────────┐     │
              │ Judge              │     │
              └─────────┬──────────┘     │
                        │                │
                  ┌─────┴─────┐          │
                  │           │          │
                PASS         FAIL ───────┘
                  │
                  ▼
                 Done
```

这三个 Agent 的**权责边界非常干净**：

> **Clarifier：定义“完成是什么”。**
> **Executor：负责“把它做出来”。**
> **Judge：负责“证明它完成了”。**

这其实就是你这个 Orca 最值得加的一层。

而且还有一个很关键的设计：**Clarifier 的输出应该是结构化 Specification，而不是一段自然语言总结。**

例如：

```json
{
  "goal": "增加订单删除接口",
  "acceptance_criteria": [
    "管理员可以删除订单",
    "已支付订单禁止删除",
    "删除采用软删除",
    "删除操作记录审计日志"
  ],
  "constraints": [
    "遵循现有 REST API 风格",
    "遵循现有鉴权机制"
  ],
  "assumptions": [],
  "open_questions": []
}
```

然后 **Judge 直接拿这个 Specification 当验收标准**。

这样三个 Agent 就真正串起来了，而不是三个各自“聊一遍”的 LLM。
